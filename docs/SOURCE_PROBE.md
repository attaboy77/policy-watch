### B. 금융감독원 (fss.or.kr)

- **⚠️ FSS User-Agent 차단 — 해결(결정 완료)**: `fss.or.kr`은 UA 문자열에 "Bot"/"PolicyWatchBot"이 포함되면 **TCP 응답 자체가 없음(curl exit 28, timeout)**. 순수 브라우저 UA는 즉시 302 정상 응답. 여러 변형을 테스트한 결과 WAF가 UA 문자열의 특정 패턴(대략 "Bot"이라는 단어)만 걸러내는 것으로 판단됨 — 일반적인 비-브라우저성 자체를 막는 게 아님(`curl/8.0`도 차단되지만 "bot"이 없는 다른 커스텀 UA는 통과 가능성 있음, 실제로는 브라우저 UA에 연락처만 덧붙인 형태로 검증).
  → **결정(사용자 확인 완료)**: robots.txt를 먼저 확인(아래) → 대상 경로가 비허용 목록에 없음을 확인한 뒤에만 **`fss.or.kr` 도메인 한정**으로 다음 UA를 사용한다. 신원을 숨기지 않도록 연락처를 그대로 남긴다:
  ```
  Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36 (contact: alchem1024@gmail.com, project: policy-watch)
  ```
  이 UA로 302(홈)·200(B1 정적 페이지)·200(B2 게시판, 실제 행 7건 확인) 모두 재검증했다. **요청 간격은 2초 이상**(SPEC 기본값 0.5~1초보다 보수적으로) 유지한다. `_http.py`에 도메인별 UA/간격 오버라이드를 추가할 것(Phase 3B 구현 항목).
  robots.txt는 `User-agent: Yeti`(네이버 봇) 그룹만 존재하고 일반(`*`) 규칙이 없으며, 어느 해석으로도 우리 대상 경로(`/fss/bbs/B0000155/...`, `/fss/main/contents.do`)는 비허용 목록(`/bos/`, `/upload/`, `/fss/cvpl/stepNotice/`, `/fss/cvpl/extincNotice/`)에 해당하지 않아 진행해도 된다.
- **B1**: `GET /fss/main/contents.do?menuNo=201174` — "내부회계관리제도 기준" 정적 페이지. `<h1>내부회계관리제도 기준`, 하위 섹션 제목으로 "감사인의 검토·감사", "모범규준", "평가 및 보고 지침" 등 확인. 변경이 드문 정적 페이지이므로 스냅샷 diff 방식(내용 해시 비교) 수집이 적합.
- **B2**: `GET /fss/bbs/B0000155/list.do?menuNo=201177` (게시판 ID `B0000155`). 실제 행: `내부회계관리제도 관련 FAQ('25.12)`, `내부회계관리제도 평가·보고 지침 Clean ver. ('24.12.23 개정)`, `연결내부회계관리제도 평가·보고 대상범위 선정 가이드라인` 등 — **SPEC-ADDENDUM 예시(§4-3의 attachments 샘플)와 정확히 일치하는 실제 데이터**. `<td class="title">` 안에 제목+링크, 상세는 `/fss/bbs/B0000155/view.do?nttId={ID}&menuNo=201177`.
- FSS 보도자료 본판(참고용, B와 무관하지만 발견): `B0000188/list.do?menuNo=200218`. FSS는 "보도자료 API"도 홍보하고 있으나(`/fss/api/apiInquiryBodoInfo/`) 페이지 안내 내용만 있고 실제 오픈API 신청 승인이 필요해 보여 Phase 3B에서는 HTML 목록으로 우선 구현.

### D1. 기획재정부 (moef.go.kr) — 재조사 결과 (목록 페이지 해결)

- **도메인 리다이렉트**: `moef.go.kr`, `www.moef.go.kr` 모두 **`mofe.go.kr`로 301 영구 리다이렉트**된다(재정경제부 시절 구 도메인). 최종 접근 도메인은 `mofe.go.kr`.
- **⚠️ 명칭 표기 함정(결정 완료)**: `mofe.go.kr` 페이지의 `<title>`, `<meta name="author">`, `og:title`, 심지어 법제처 Open API 응답의 `소관부처명` 필드까지 전부 **"재정경제부"**(2008년 이전 명칭)로 남아있다. SPEC-ADDENDUM §2-D1이 미리 경고한 상황 그대로다. **→ `source.name`은 페이지/API에서 절대 스크래핑하지 않고 `_config.py`에 `"기획재정부"`로 고정값 지정한다(사용자 확정 지시).**

  ```html
  <li>
    <h3><a href="javascript:fn_egov_select('MOSF_000000000079100');">아시아인프라투자은행(AIIB)과 개발사업 협력 및 인적교류 강화</a></h3>
    <div class="boardInfo">
      <div class="infoLeft">
        <span class="date">2026.08.24.</span>
        <span class="depart">국제기구과</span>
      </div>
    </div>
  </li>
  ```
  즉 **제목 / 날짜(`class="date"`) / 담당부서(`class="depart"`) / ID(`MOSF_...`, onclick 인자에서 정규식 추출)** 4요소 모두 목록 페이지에서 추출된다. 실제 항목 10건 확인(예: "[보도참고] 조세지출결산서 최초 작성 및 국회 제출" 등 세제 관련 보도자료 포함).

### D3. 정책브리핑 (korea.kr) — 통합 수집기 특이사항

- `GET /briefing/pressReleaseList.do` — 서버 렌더링 HTML, 각 항목이 `<li><a href="/briefing/pressReleaseView.do?newsId={ID}...">` 안에 `<strong>제목</strong>`, `<span class="lead">본문 요약</span>`, `<span class="source"><span>날짜</span><span>부처명</span></span>` 구조로 완결 — **제목/날짜/부처명/링크 4요소 모두 목록 페이지에서 추출 가능**함을 실제 데이터로 확인(예: "기획예산처" 항목).
- **⚠️ 부처 체크박스 필터(`deptCode`) 미작동**: 페이지에 `<input type="checkbox" name="deptCode" value="B00004" title="국세청">`(국세청), `value="C00003" title="금융위원회"`(금융위원회) 형태의 필터 UI가 존재하지만, `?deptCode=B00004` GET과 동일 파라미터 POST 모두 결과가 필터링되지 않았다(전체 목록 그대로 반환). JS/AJAX 기반 클라이언트 필터로 추정.
  → **대안**: 필터를 쓰지 않고 전체 목록을 페이지네이션으로 수집한 뒤, 각 항목의 `span.source` 두 번째 `<span>` 텍스트(부처명)가 `{"기획재정부", "국세청", "금융위원회", "금융감독원"}`에 포함되는지로 **사후 필터링**한다. `_utils.classify()`와 동일한 패턴.
- **⚠️ 부처 커버리지 확정**: `deptCode` 체크박스 전체 목록(58개 부처/기관)을 확인한 결과 **"금융감독원"은 존재하지 않는다** — FSS는 정부 부처가 아닌 별도 기관이라 정책브리핑 집계 대상이 아님(확정, 재확인 불필요). **"기획재정부"도 체크박스 목록에 없고 구 명칭 "재정경제부"만 존재** — 즉 정책브리핑에서 기획재정부 보도자료가 부처명 "기획재정부"로 정확히 태깅되는지 이번 조사에서 표본 내 실증하지 못했다(당일 목록 샘플에 미등장). 사후 필터링 매커니즘 자체는 다른 부처("기획예산처")로 검증되었으므로 구조적으로는 동작하나, 표기 명칭 변형("기획재정부" vs "재정경제부")에 대비해 두 문자열 모두 매칭 대상에 넣을 것을 권장한다.

### D4. 법제처 Open API (law.go.kr) — 완전 검증

- `GET https://www.law.go.kr/DRF/lawSearch.do?OC={OC}&target=law&type=XML&query=법인세법` — **더미 값 `OC=test`로도 실제 XML 응답**을 받았다(`totalCnt=3`, `resultCode=00`). 로컬(한국 IP) 기준 프록시 없이 정상 동작.

- **⚠️ SPEC-ADDENDUM-3 §4-1 대응 — 법령명 화이트리스트 조회 검증(추가 조사)**: `tax_subjects.yml`의 `laws:` 목록(법인세법, 부가가치세법, 소득세법, 국제조세조정에 관한 법률, 조세특례제한법, 지방세법)을 `query=` 파라미터로 직접 넣어 6건 모두 조회 성공(각 법률의 본법/시행령/시행규칙 3건씩 반환). **다만 법제처 API의 `query`는 부분일치(substring)이며 정확히 일치하는 검색이 아니다** — 예를 들어 `query=지방세법`은 무관한 `지방교부세법`(및 시행령·시행규칙)까지 총 6건을 반환했다. → ADDENDUM-3이 기대하는 "법령명 목록으로 직접 조회하면 오탐이 원천적으로 없다"는 전제는 **API 응답의 `법령명한글`이 목록의 문자열과 정확히 일치하는 것만 채택하는 클라이언트측 필터를 반드시 추가해야** 성립한다(또는 API의 `search=2`형 정확일치 옵션이 있는지 Phase 3D에서 재확인). 이 단서를 달면 화이트리스트 방식 자체는 유효하고 결과도 좋다.

## A2(K-IFRS 기준서 목록) 재검토 — 수집 대상에서 제외 확정 (2026-08-26)

사용자가 "A2 76건이 최근 변경분인지 전체 카탈로그인지" 확인을 요청해 실제 데이터를 다시 열어봤다. 두 가지가 확인됐다.

1. **정적 전체 카탈로그가 맞다.** 76건 전부 `재무회계개념체계`, `제01장 목적, 구성 및 적용`, `제19호 리스`, `제5001호 결합재무제표` 같은 챕터/호수 제목이고 날짜 컬럼 자체가 없다(기존 조사에서도 확인했던 사실). 매 실행마다 정확히 같은 76건이 나오므로 "최근 90일 내 변경"으로 걸러낼 방법이 없다 — 대시보드 취지("새로 바뀐 것 파악")와 맞지 않고, A1의 실제 변경 항목이 이 76건에 묻힌다는 우려가 맞았다.
2. **더 근본적인 문제: 애초에 K-IFRS가 아니다.** 위 제목들의 "제NN장"/"제NN호"/"제5NNN호" 번호 체계는 **일반기업회계기준**(비상장 중소기업용 K-GAAP)의 것이다. K-IFRS 기준서는 "K-IFRS 제1116호"처럼 1000번대로 불리는데 76건 중 1000번대는 하나도 없다. SPEC-ADDENDUM.md §2-A2가 기대한 "K-IFRS 기준서 목록"과는 다른 게시판을 짚었던 것으로 보인다.

**결정: A2를 수집 대상에서 제외한다**(사용자 제시 옵션 중 두 번째). K-IFRS 제·개정 소식은 A1(comm010, category="회계기준소식")이 이미 실제로 잡아내고 있다 — 예: "IASB 공개초안 '위험경감회계'"(K-IFRS/IASB 관련), 날짜·본문 다 있어 A2보다 실용적이다. `kasb.py`의 `fetch()`에서 `fetch_standards()`(A2) 호출을 뺐고, 함수 자체는 향후 진짜 K-IFRS 기준서 목록 게시판을 찾을 경우를 대비해 코드만 남겨뒀다(위 상세 사유는 함수 docstring에 기록).

**추가 결정(2026-08-26, 후속 지시로 반영 완료)**: A3(질의회신요약)의 상단 고정 6건("일반기업회계기준 질의회신 비교표" 등)도 우리 대상(K-IFRS 적용 대상)이 아니므로 제외했다. `fetch_qna()`에서 `published_at`이 없는 항목(=상단 고정 계열, 날짜 유무가 정확히 일반기업회계기준 여부와 일치함을 확인)을 걸러내도록 구현 — 16건 → 10건, 전부 K-IFRS 관련(예: "K-IFRS 제1118호 정착지원 TF 논의 내용", 1000번대 확인)으로 검증됨.

### 이번 확인으로 얻은 설계 시사점

1. **"본문이 HTML에 있는 소스"와 "첨부파일 안에만 있는 소스"가 명확히 갈린다.** KASB(A1~A3)·법제처(D4)는 본문/필드가 그대로 노출되어 `effective_date` 자동 추출 기대치가 높다. FSS(B2)·MOEF(D1)·NTS(D2)는 실제 내용이 첨부 HWP/PDF 안에 있어 SPEC §4-3(첨부파일 다운로드·파싱 금지) 방침을 지키는 한 이 소스들의 `effective_date`는 구조적으로 `null`이 많이 나올 수밖에 없다 — **이건 구현 버그가 아니라 소스 특성이므로, `data/schedules_manual.yml` 수동 보완이 이 세 소스에 한해 필수 운영 프로세스가 된다**는 점을 미리 인지해야 한다.
2. **세법(`tax`) 카테고리의 시행일 신뢰 소스는 사실상 D4(법제처) 하나로 좁혀진다.** D1(기재부)·D2(국세청)는 발표/발간 사실은 잘 잡히지만 시행일은 못 뽑는다. 세법 카테고리 우측 캘린더(§7-4)에 올라갈 정확한 시행일정은 법제처 API 항목 위주로 채워질 가능성이 높다는 뜻이다.
3. **KASB의 "공지사항" 카테고리는 doc_type 판정 대상에서 아예 빼야 한다.** "본인 인증 서비스 일시 점검 안내" 같은 운영성 공지가 섞여 있어(A1 실제 확인), `classify()`/`doc_type_of()` 이전 단계에서 카테고리="공지사항"인 항목은 걸러내는 필터를 추가하는 게 맞아 보인다(ADDENDUM-2/3에는 명시 안 됐지만 실측 기반 권장 사항).

- JS 렌더링 여부: 모든 목록 페이지가 서버 렌더링 HTML이었음(SPA 없음). MOEF는 처음엔 grep 패턴이 맞지 않아 "렌더링 안 됨"으로 오판했으나(위 D1 참고), 실제로는 `fn_egov_select()` onclick 패턴의 서버 렌더링 HTML — jQuery 기반 구세대 스택이라 JS 실행 없이도 최초 GET 응답에 데이터가 전부 들어있었다.
